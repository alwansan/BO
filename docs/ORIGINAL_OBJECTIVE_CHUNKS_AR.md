# أجزاء قيم أهداف المهمة — Chat-Batch05

الأساس: `alwansan/BO:experiment/black-coop` عند
`f7551ada9e7e352f937bd24e7b5ba405b947602d`، بعد Chat-Batch04 المحلي.
هذه دفعة codec وتجميع ببيانات اصطناعية. لا نوع رسالة RoomWire جديد،
ولا اتصال TLS أو تشغيل Android أو محرك BLACK.

## لماذا هذه الحدود؟

[RoomWire](https://github.com/alwansan/BO/blob/f7551ada9e7e352f937bd24e7b5ba405b947602d/coop/lobby/java/com/racas/black/coop/RoomWire.java)
يحد الإطار الكامل إلى 512 بايتًا، منها 8 للترويسة الخارجية، فيبقى
504 بايتات للجسم. لم يتغير VERSION/PROFILE=9 أو أعلى نوع OBJECT_EVENT=16.

[RoomTls](https://github.com/alwansan/BO/blob/f7551ada9e7e352f937bd24e7b5ba405b947602d/coop/lobby/java/com/racas/black/coop/RoomTls.java)
يستخدم طابور تحكم سعته 8، ومرجعين مستقلين لأحدث جزأي NPC. لا يوجد فيه
مرسل لقطة أهداف من عشرات الأجزاء. التوصيل الفعلي لاحقًا يحتاج وحدة إرسال
immutable لكل ضيف، ومؤشر جزء، وأولوية للتحكم، وإلغاءً عند PREPARE/ABORT
وتغير roster، مع تحديث توافق البروتوكول واختبارات sockets مستقلة.

لم تتغير قائمة Java في
[prepare_room_network.py](https://github.com/alwansan/BO/blob/f7551ada9e7e352f937bd24e7b5ba405b947602d/coop/prepare_room_network.py).
وجود المصدر الجديد هنا لا يعني إدخاله في APK أو تفعيل مصرف native.

## صيغة body المقترحة والمختبرة محليًا

`RoomObjectiveChunks` ينتج أجسام أجزاء فقط؛ لا ينشئ `RoomWire.Packet` ولا
يعطيها رقم نوع أو إصدارًا مستقلًا يمكن إرساله في البروتوكول الحالي.

| الحقل | الحجم والترتيب |
| --- | --- |
| Ticket كاملة | 36 بايتًا بنفس ترتيب RoomStoryWire، BE للأعداد |
| sequence | 8 بايتات BE؛ long موجب خاص بنشر لقطات المود |
| totalRecords | بايتان BE؛ من 0 إلى 4096 |
| partIndex | بايتان BE؛ يبدأ من صفر |
| SHA-256 | 32 بايتًا لبصمة كل بايتات سجلات اللقطة الكاملة |
| records | كل سجل 16 بايتًا: ID خام8، ثم counter LE32 وstate LE32 |

حجم metadata هو 80 بايتًا، لذلك يتسع الجزء إلى 26 سجلًا. جسم الجزء الكامل
496 بايتًا، ومع الترويسة الخارجية المستقبلية يصبح 504 بايتات، تحت حد512.
4096 سجلًا تحتاج 158 جزءًا؛ الأخير يحوي 14 سجلًا. اللقطة الفارغة لها
جزء واحد بفهرس صفر وبصمة SHA-256 للسجلات الفارغة.

طول كل جزء مشتق من العدد الكلي والفهرس. لا يكفي أن يكون تحت الحد؛ يجب
أن يكون بطوله الدقيق، دون سجل مبتور أو trailing bytes.
حدود counter/state ما زالت حدود مرجع checkpoint الموضحة في Batch03؛
لا تعني إثبات جميع حالات الأهداف الحية على Android.

## التجميع والترتيب

يرتبط كل Assembler بتذكرة مستقلة وجدول IDs مستقل منسوخ. يحتفظ بلقطة
جزئية واحدة ولقطة مكتملة واحدة. لا ينشر المكتملة إلا بعد توافر كل
الأجزاء والتحقق من الهوية والقيم وبصمة المحتوى الكامل.

`highWater` هو أعلى sequence بدأ بجزء صفر مقبول، وليس ساعة محرك أو
آخر لقطة مكتملة. جزء غير أول من sequence أعلى لا يبدأ تجميعًا ولا
يسقط اللقطة الجزئية الحالية. الجزء الأول المقبول من sequence أعلى
يستبدل الجزئية الأقدم؛ الأجزاء الأقدم تُرفض بعده.

الأجزاء مطلوبة بترتيبها. نسخة مكررة مطابقة لا تزيد التقدم؛ نسخة متعارضة
أو gap أو metadata متضاربة تسقط الجزئية مع الاحتفاظ برقمها. لا يمكن
إحياء الرقم نفسه بعد إكماله أو إسقاطه؛ التعافي يحتاج لقطة برقم أعلى.
لا ادعاء بتحمل إعادة ترتيب الأجزاء.

تمنع البصمة جمع أجزاء غير متداخلة من محتويين مختلفين تحت sequence واحد؛
مقارنة الأجزاء المكررة وحدها لا تكفي لهذا. دور SHA-256 هنا مطابقة
المحتوى، وليس إثبات مصدر أو مصادقة. لم يتغير أي تحقق TLS أو ضابط أمني.

قد تبقى آخر لقطة مكتملة متاحة أثناء وصول لقطة أحدث منها. تُعرّف برقمها؛
لا يوجد TTL أو ضمان freshness زمنية. sequence موجب ولا يلتف عند
Long.MAX_VALUE. رقم جديد من البداية يحتاج Ticket جديدة مستقلة.

تغيّر currentTicket المستقلة أو اختفاؤها، أو abort، يلغي instance نهائيًا.
أما تذكرة أجنبية داخل body مع currentTicket صحيحة فتُرفض دون تغيير
حالة المهمة الحالية. إنشاء instance جديد لنفس Ticket يفقد highWater؛
المستهلك المستقبلي يجب أن يحتفظ بالحالة طوال التذكرة أو ينشئ تذكرة
جديدة، لا يعيد الرقم لنفس التذكرة بعد reconnect.

اللقطات والأجزاء المنشورة تملك بياناتها وتعيد نسخًا عند طلب بايتاتها.
Assembler مقيد بخيط مالكه؛ لا يقدم مشاركة mutable بين خيوط الشبكة
واللعبة. النقل المستقبلي بين الخيوط يجب أن يمر بنتيجة immutable واضحة.

## التحقق وإعادة التنفيذ

`RoomObjectiveChunksTest` يختبر حدود الأجزاء، وgolden bytes مستقلة،
والتكرار والفجوات والمزج وتبدل التذكرة والتسلسل والإلغاء، باستخدام
Ticket الفعلية في Java وبيانات اصطناعية فقط.

`test_room_objective_chunks_interop.cpp` يولد 4096 سجلًا من وحدة C++ في
Batch03/04، بمعرفات فيها البت الأعلى، ثم يمررها إلى اختبار Java.
تجمعها ثلاثة مستقبلات اصطناعية مستقلة. يعيد C++ قراءة نواتجها ويتحقق
من كل ID/counter/state بواسطة Prepare الموجود وجدول IDs مستقل مولد
من تعريف fixture، لا من البيانات الواردة.

ملفات التبادل بين اللغتين تحوي records فقط؛ يعيد fixture في C++ بناء
scope من تعريفه المحلي. لذلك فهذا roundtrip للقيم، وليس اختبار نقل
metadata التذكرة بين Java وC++. تغطي Ticket الفعلية وgolden المستقلة
صيغة metadata ومطابقتها في اختبار Java.

```sh
python3 source/coop/room_network/check_objective_chunks_interop.py --source-root source --output chunks-results --java-current-runtime --disable-leak-check
```

الأمر أعلاه يستخدم Java runtime الحالي صراحةً، وفحص C++ مع ASan/UBSan
دون LSan بسبب قيد ptrace المثبت سابقًا. احذف --java-current-runtime في
JDK يدعم الهدف الافتراضي --release 8؛ واحذف --disable-leak-check عندما
يدعم runtime فحص التسرب. لا يدّعي التحقق المحلي بناء Java8 أو Android.
خطوة CI المحلية تستخدم الخيارين الافتراضيين ولم تُشغّل أو تُنشر.

أدلة التنفيذ الفعلي وبصمات المصادر والfixtures محفوظة في حزمة الدفعة.
نجحت المجموعات الاثنتا عشرة في Java، ونجح توليد C++ ثم تحققه من ثلاث
نتائج مستقلة، كل منها 4096 سجلًا/65536 بايتًا، جُمعت من 158 جزءًا.
تطابقت SHA256 لملفات سجلات الضيوف الثلاثة مع ملف المضيف الاصطناعي.
اختبار C++ نُفّذ مع ASan/UBSan؛ Java نُفّذ على runtime21 المتاح بخيار
صريح. أنشأ checker مجلد عمل جديدًا لكل تشغيل لمنع نجاح مبني على بقايا
class files أو ملفات نتائج قديمة.
لم تُعد اختبارات C++ الثمانية أو مقارنة scope السابقة عندما ظلت
اعتمادياتها دون تغيير.

## ما يبقى بعد هذه الدفعة

الخطوة التالية هي توصيل الأجزاء إلى مسار RoomTls الفعلي مع تحديث
التوافق وتجهيز المصدر، وإدارة إرسال bounded لا تملأ طابور التحكم،
والإلغاء على دورة حياة القصة. يجب اختبار مضيف وثلاثة ضيوف عبر sockets
حقيقية بمنتج أهداف اصطناعي، بما يشمل COMMIT/ABORT وتبدل roster أثناء
لقطة كبيرة. نجاح codec وتجميع ملفات هنا ليس دليلًا على ذلك النقل.

منتج الأهداف الحية وعمر جدولها وتطبيق آثارها الأصلية ما زالت غير مثبتة.
لا استخدام checkpoint loader أو تعديل قواعد الأهداف كبديل، ولا تغيير
لذكاء الأعداء والحلفاء أو الأصول أو الحفظ. لا دفع أو نشر أو اختبار
هاتف صغير؛ تجربة قبول واحدة بهاتفين بعد اكتمال المسار المتفق عليه.
